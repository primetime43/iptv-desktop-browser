# Dashboard structure

The dashboard is being migrated in stages. The running UI uses these page views in `DesktopApp/Views/Dashboard`:

| Page | View model | Existing interaction code |
| --- | --- | --- |
| Live TV | `LiveTvPageViewModel` | Bound category/search/loading state; shell handles playback and XMLTV presentation |
| Movies and series | `MoviesSeriesPageViewModel` | Bound category/search/loading state; shell handles layout and player integration |
| Movie/series details | `MediaDetailsViewModel` | `MediaDetailsView` bindings and playback request events |
| Scheduler | `SchedulerPageViewModel` | `DashboardWindow.Scheduler.cs` |
| New recording form | `RecordingFormViewModel` | `RecordingFormView` bindings; `RecordingFormInteraction` handles dialogs |
| Existing recordings | `RecordingManagementViewModel` | `RecordingManagementView` commands; `RecordingEditWindow` / `RecordingEditViewModel` for edits |
| Series recording dialogs | `SeriesRecordingDialogViewModel`, `SeriesScheduleViewModel` | `SeriesRecordingWindow` and `SeriesScheduleWindow` bindings |
| Settings | `SettingsPageViewModel` | Bound commands; `SettingsInteraction` handles Windows dialogs/processes |

`DashboardWindow` remains the shell. `DashboardNavigationViewModel.ActivePage` and `MoviesSeriesPageViewModel.ContentType` represent navigation explicitly. Button colors and control visibility are presentation outputs, not inputs to content-loading decisions. Viewport geometry still determines which thumbnails and guides to prioritize within the active page.

Page view models own catalog collections, collection views, selection state, and catalog request coordinators. Live TV, Movies/Series, and Scheduler inherit the shell's data context and bind to the appropriate page model. Category pickers and search fields bind directly to the page models, without window selection handlers. Remaining playback, recording, and layout handlers forward through the owning window. `DashboardWindow.PageControls.cs` adapts their XAML namescopes for that platform interaction code.

`LiveTvPageViewModel` owns category loading, selected category, local filtering, debounced global search, counts, errors/retry, and request lifetimes. `ILiveCatalogSource` isolates the current account's provider, playlist, and favorite mapping. Playlist IDs and guide IDs are preserved, including the `Other` category. Global queries share one index task per active page lifetime; successful indexes are retained for that window. Superseded searches cancel their waits, and leaving the page cancels the underlying pending index request. Results are detached copies, so displaying a subset cannot renumber or mutate the search index. Clearing global search restores the selected category, and typing a local query while a category downloads does not restart that download.

`MoviesSeriesPageViewModel` owns both category lists, independent movie/series category selections, the VOD search query, filters, counts, request state, and retry. It calls `IVodService` and uses its existing caching/parsing path. Successful empty lists are explicitly retained rather than treated as not yet loaded. Switching type retains each picker and successfully loaded catalog; interrupted catalogs resume on return. Category endpoints fail and retry independently. The old Xtream catalog mirrors in static `Session` are no longer populated; the page collections and service cache hold that data. The session's M3U data remains an input to `VodService`.

Navigation activates/deactivates each model for both clicked and programmatic page changes. `LatestRequestLoader` checks the active request and current category/type before applying results, errors, or completion state. Disposal cancels outstanding requests; changing the category, filtering out the selection, or leaving VOD clears obsolete details. Safe user-facing errors and loading overlays bind directly to model state; diagnostic exceptions flow to the shell's redacted logger.

`DashboardWindow.CatalogLoading.cs` is the WPF viewport adapter. It reads realized controls and sends selected/visible/nearby demand to the existing bounded `CatalogResourceLoader`. It rejects rows that no longer belong to the current filtered collection and excludes loading catalogs. Page models raise resource-demand notifications when catalog state changes; geometry, dispatcher timing, and the recording scheduler bridge remain in the shell.

Settings binds directly to `SettingsPageViewModel`. The model owns the editable draft, validation messages, player choice, and commands for saving/restoring, browsing/testing players, EPG refresh, and cache clearing. It has no control lookups, window references, or direct access to static session state. `IApplicationSettingsService` supplies detached settings snapshots and persists a validated snapshot before updating the session. Explicit save failures propagate to the editor. The disk-cache checkbox retains its existing immediate behavior; loading the draft does not toggle it. `ISettingsInteraction` isolates filesystem checks, native dialogs, executable detection, and process launching. Tests replace these dependencies without opening dialogs or touching user settings.

The Settings view raises host events for favorites import/export and opening the shared cache inspector. It does not reference `DashboardWindow`. Navigation activates the settings editor through `SettingsPageModel.Load()`, including programmatic page changes. Log controls belong to the separate Logs page; their existing handlers are now in `DashboardWindow.Logs.cs`.

`MoviesSeriesPageViewModel.Details` owns the single movie/series selection and its explicit empty/loading/ready/failed state. `MediaDetailsView` binds directly to that model, with no window lookup or per-title property-change subscriptions. The model uses `IVodService` and `SelectedDetailsLoader` for detached, guarded requests, shares repeated selections, and supplies a retry command. Content-type commands clear obsolete details; category changes, page departures, and window closure clear them through the existing shell lifecycle. Playback commands raise typed requests handled by the shell's existing player integration.

Details metadata, season headers, and episodes form one flat list with a WPF recycling panel. A single batch replaces its rows, and scrolling realizes only nearby episode controls. Keep this list out of an outer `ScrollViewer` or `StackPanel`, which would remove its bounded viewport. Episode commands reject stale rows from a previously selected series.

`SchedulerPageViewModel.NewRecording` owns the scheduling draft: explicit guide/custom mode, channel/program selection, dates and times, title, buffers, output path, validation, and commands. `RecordingFormView` binds directly to that model; its only pointer handlers preview a hovered program's airtime. Live indicators use a display wrapper and never alter the underlying EPG title. A browsed output path is retained while editing the draft. The draft resets only after successful submission; declined conflicts and failures preserve it.

`IRecordingScheduleService` adapts session stream URLs and the existing recording scheduler. Its guide path reuses `IChannelService` on a detached channel off the UI thread, or snapshots the local M3U guide. The form prepares and batches at most 50 upcoming programs. `LatestRequestLoader` cancels superseded loads and guards their application by active page, mode, and channel identity. Shell navigation activates/deactivates the form, including programmatic navigation and window closure. Conflict confirmation and file browsing are isolated in `IRecordingFormInteraction`, so regression tests never launch recorders or open dialogs.

`SchedulerPageViewModel.Recordings` owns existing-recording management. `IRecordingManagementService` exposes a read-only observable wrapper around the scheduler's live collection. Commands handle properties, editing, cancellation, cleanup, and opening the output folder. `RecordingEditViewModel` holds a detached title/buffer draft, validates it, and returns an explicit result; the platform interaction displays the dialog. Saving preserves series/EPG identifiers and recording metadata. Commands recheck record identity and status after modal dialogs, since the scheduler or account may change while a dialog is open.

The recordings grid is read-only so cell edits cannot bypass persistence. The scheduler's tab host and management view supply a finite viewport, letting the DataGrid recycle rows rather than expanding inside outer scroll containers. Collection changes update status subscriptions incrementally, status changes invalidate commands on the UI dispatcher, and closing the shell disposes those subscriptions. File/process operations remain behind desktop interaction services.

Series recording dialogs use dedicated XAML windows and detached view models. The add/edit model owns channel selection, normalized guide suggestions, manually entered names, next-airing text, validated buffers, retry, preview, and save/cancel commands. Editing retains the channel and returns a draft; the shell checks that the original rule still exists before persisting it. Edits apply to future scheduling and preserve recording history and already scheduled episodes. `SeriesScheduleViewModel` provides empty/loading/error states and a bounded, recycling list of upcoming guide airings; previews describe airings, not guaranteed recordings.

Both dialogs reuse `IRecordingScheduleService`; the shared channel parser accepts the original series parser's timestamp aliases and UTC date strings. M3U rules can resolve their guide through playlist IDs when only the stored channel ID is available. Guide preparation runs in background work, with batched collections and `LatestRequestLoader` guards. Closing either window cancels outstanding requests and prevents late results from updating it. `DashboardWindow.Scheduler.cs` now only composes the dialogs, commits drafts, and bridges scheduler events. Timer callbacks enter through the dispatcher and reject guide results for rules removed or replaced during account changes.

`DashboardWindow.Playback.cs` centralizes Live TV, movie, and episode launching for the quality-selection feature. Normal playback invokes the configured player immediately. Explicit quality actions open `PlaybackQualityWindow` / `PlaybackQualityViewModel`; closing or playing cancels discovery and rejects late results. The shell rechecks selection after the modal dialog before launching. `MediaDetailsViewModel` exposes guarded movie/episode quality commands alongside playback commands.

`StreamQualityService` inspects HTTP streams with an eight-second deadline and a 256 KiB limit, rejecting media bodies without buffering them. `HlsQualityParser` resolves references against the final URL after redirects and creates one-variant masters retaining the selected rendition groups and session keys, following [RFC 8216](https://www.rfc-editor.org/rfc/rfc8216.html). Variable substitution and content steering defer to automatic playback. The parser does not infer missing qualities or invent provider URL query parameters.

`PlaybackManifestServer` serves selected master playlists from memory over an IPv4 loopback socket with random paths, no-store responses, bounded request headers/concurrency, and a maximum of 32 retained manifests. It never proxies media segments or writes credential-bearing manifests to disk. It is created only when a fixed quality is played and disposed with the window. Keeping the original master structure lets external players retain separate audio/subtitle tracks instead of receiving a video-only variant URL. Regression checks exercise parsing, bounded HTTP reads, cancellation/retry, compiled controls, stale episode commands, and actual loopback GET/HEAD requests without a provider account or player process.

XMLTV presentation, viewport geometry, favorites-page interactions, and series-list commands remain in the shell. Migrate these alongside related feature work when the extraction centralizes behavior or makes an important interaction testable; avoid splitting small, cohesive classes just to reduce line counts. Do not create a second copy of page state in the shell or add behavior to the legacy, unused `DashboardViewModel`.

Catalog parsing and preparation run in background work. UI collections use `BulkObservableCollection.ReplaceAll`, which emits one WPF-compatible reset. Keep cancellation and current-selection checks around result application; never mutate an already-bound model from background work.

`VirtualizationRegressionTests` loads the compiled page views and production templates, checks page-model bindings, and verifies bulk collection filtering/sorting. It also exercises settings commands and failure recovery, details request races/retries/cancellation, a compiled details view containing 10,000 episodes, recording-form validation and overnight scheduling, management commands, edit races, and a real scheduler tab with 10,000 recordings. Series-dialog checks cover late guide responses, close cancellation, retries, manual entry, detached edits, actual XAML bindings, and 10,000 virtualized airings. Catalog orchestration checks cover category/type races, leaving/returning, index sharing, stable numeric search, category restoration, failures/retry, playlist mapping, and actual picker/search/loading bindings. `CatalogLoadingRegressionTests` exercises background preparation, request cancellation, thumbnails, and guide loading without a provider account.
